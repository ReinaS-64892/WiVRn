WiVRn 映像パケットロス計測：初期調査
調査日: 2026-11-20
調査元: 70485093
ブランチ: investigate/video-packet-loss

目的
  FEC の方式を決める前に、映像 UDP の欠落頻度、連続性、表示への影響を測る。
  この段階では送信方式、デコード待ち時間、IDR 復旧の動作を変更しない。
  コード調査に加え、下記の計測コードと集計ツールを実装した。
  実機の無線通信で測定した結果はまだ含まない。

クライアントの統計画面で見る
  クライアントをこのブランチからビルドすると、「統計」の上部に
  「映像の受信状況」を表示する。Steam Frame・Android・Linux で共通。
  画面で見るだけなら起動オプションや環境変数は不要。
  左目・右目・使用中のアルファストリームを分けて表示する。
  受信数、遅着、バッファ内の重複、順序逆転、未完成フレーム数と割合、
  欠落パケット数の下限、総パケット数が不明なフレーム数を表示する。
  各項目のラベルにポインターを合わせると、集計の意味を表示する。
  カウンターはストリーム設定後の累計で、デコーダー再作成時にリセットする。
  受信中のフレームは、完了または破棄するまでフレーム数に加えない。
  未完成の割合はパケットロス率ではなく、受信したフレームの未完成率。
  パケットを一つも受信しなかったフレームと、送信前スキップは区別できないため、
  フレーム数・欠落数には加えない。UDP と TCP の映像を両方含む。
  欠落の下限は、観測した番号の穴の数に、末尾未受信なら最低１を加えたもの。
  破棄時点の値を保持し、遅着後も減らさない。
  遅着には重複も含む。重複数は現在・次のフレームのバッファ内だけを対象とし、
  破棄済みフレームについて無制限の履歴を保持することはしない。
  正確なパケットロス率や全フレーム消失の調査には、以下の両端ログ計測を使う。

画面表示追加の検証結果
  Linux x86_64 のクライアント全体を client プリセットでビルド・リンクできた。
  CTest の video-receive-stats / video-packet-audit / video-packet-loss-report が成功。
  画面用カウンターは欠落・末尾未受信・重複・遅着・未受信フレームの除外・
  未確定フレームの除外・初期化・別スレッドからの読み取りを検証した。
  AddressSanitizer / UndefinedBehaviorSanitizer でもカウンターのテストが成功。
  日本語翻訳の msgfmt 検査と、ビルド時の翻訳ファイル生成が成功。
  Steam Frame / Android の実機での表示と、計測負荷は未検証。

  WIVRN_BUILD_TEST=ON でビルドした場合の実行例:
    ctest --test-dir <ビルドディレクトリー>/common -R 'video-' --output-on-failure

クライアントのボタンでログを保存する（Steam Frame 推奨）
  接続中に「設定 → システム」または「統計」を開き、
  「パケットログの記録を開始」を押す。10〜30秒程度操作してから、
  同じボタンで記録を停止する。再起動・起動オプション・stdout の回収は不要。
  ボタンの下に記録中／保存完了／エラーと、実際の保存先を表示する。
  記録は現在の接続内だけで有効。記録を開始するたびに新しいファイルを作り、
  過去の記録は上書きしない。ディスクへの書き込み失敗も画面に表示する。

  Linux / Steam Frame の保存先:
    $XDG_STATE_HOME/wivrn/logs/video-packets-<一意な番号>.log
  XDG_STATE_HOME が未設定・空・相対パスの場合:
    ~/.local/state/wivrn/logs/video-packets-<一意な番号>.log
  XDG_STATE_HOME はログ等の永続的な状態データ向けの標準ディレクトリー。
  設定フォルダーは使用しない。画面に出たファイルを SSH / scp 等で回収する。
  Android はアプリ用外部ストレージの files/logs/ を使用し、利用できない場合は
  Android の実際のキャッシュディレクトリー内の logs/ を使用する。

  PC 側は下記の WIVRN_PACKET_AUDIT=1 によるサーバーログを取得しておく。
  ボタンで保存したファイルを、集計コマンドの client-audit.log の代わりに渡す。
  開始前に一部受信したフレームと、停止時にまだ未確定のフレームは比較対象から
  除外する。記録した範囲だけを PC 側のログと照合するので、前後の時間帯を
  パケットロスに数えない。この機能には更新した集計ツールを使う。
  短すぎる記録は「確定したフレームがない」等のエラーになるので、長めに記録する。
  通常の切断でもログを終了する。強制終了では end が欠ける可能性がある。

実装済みの環境変数によるログ計測を使う
  PC と HMD の両方で、このブランチのコードを通常の手順でビルドする。
  プロトコルは変更していないが、両端の計測ログが必要。
  初回は短い 30〜60 秒程度の接続１回で試す。

  PC サーバーを起動するシェルで、環境変数を設定してログを保存する。
    WIVRN_PACKET_AUDIT=1 XRT_LOG=info wivrn-server > server-audit.log 2>&1
  実際に起動するのは、このブランチからビルドしたバイナリー。
  ダッシュボード等から起動する場合も、サーバープロセスに変数を渡す。

  Android HMD では、WiVRn を起動・接続する前に以下を実行する。
    adb shell setprop debug.wivrn.packet_audit 1
    adb logcat -v threadtime '*:S' WiVRn:I > client-audit.log
  ２つ目のコマンドは別ターミナルで実行し、計測中は動かしておく。
  既に接続中なら、いったん切断して接続し直す。
  Linux クライアントの場合は次のように起動する。
    WIVRN_PACKET_AUDIT=1 wivrn > client-audit.log 2>&1

  普段の操作をした後、HMD の操作で正常に切断する。
  サーバーを正常終了させてから、logcat の保存を止める。
  両端の WIVRN_PACKET_AUDIT 行に begin / frame / end があることを確認する。
  INFO ログを抑止すると計測できない。Android プロパティを読めない場合も
  begin 行は出ないため、その状態での「ログなし」をロスゼロと扱わない。

  集計（Python 3、追加パッケージ不要）:
    python3 tools/video-packet-loss.py server-audit.log client-audit.log --stream 0
    python3 tools/video-packet-loss.py server-audit.log client-audit.log --stream 1
  stream は 0=左目、1=右目、2=alpha。
  再接続などで候補が複数ある場合は、エラーに列挙される ID を指定する。
    python3 tools/video-packet-loss.py server-audit.log client-audit.log --stream 0 --tx-capture 3 --rx-capture 1
  ID は各プロセス内だけの番号であり、両端で同じ値になるとは限らない。
  同じ接続のログ同士を選ぶ。別プロセス起動分を１ファイルに連結しない。

  計測後は Android の設定を戻す。
    adb shell setprop debug.wivrn.packet_audit 0
  PC / Linux は環境変数を付けずに再起動すれば無効になる。

出力の読み方
  udp_missing_at_retirement_percent:
    再構成を見切ったフレームの、OS に送信を受理された UDP shard に対する
    見切り時点の未着率。後から届いたものもこの未着率には含む。
  udp_received_late_unique:
    見切り後に初めて届いた shard 数。通常受信の後の重複はここには含めない。
  udp_not_received_by_capture_end:
    送信成功扱いの UDP shard のうち、クライアントの計測終了まで未受信の数。
    両端で接続全体のログが揃っていることが前提。無線区間だけのロスではない。
  send_failed_or_inactive / tcp_accepted:
    送信例外・無効な接続での送信と、TCP に送った映像を別集計する。
  unfinalized_frames:
    切断時にも再構成を見切っていない末尾のフレーム数。
    これらは見切り時点の未着率の分母・分子に入れない。
  missing_per_finalized_udp_frame / missing_per_8_shard_group:
    フレームごと、およびフレーム内の shard 番号を８個ずつ区切った欠落数分布。
    パリティ自体の欠落を含む FEC シミュレーションではない。
  max_consecutive_missing_in_frame:
    同一フレーム内で連続して欠けた UDP shard の最大数。
  rx_duplicates_all_transports / rx_out_of_order_all_transports:
    受信した全映像 shard の重複数と、既に見た最大番号より古い到着数。
    後者には重複も含み、TCP の映像も対象になる。
  per_tx_second:
    サーバー側キャプチャ開始から１秒単位の送信数・未受信数・遅着数。

計測の仕組みと制限
  common/video_packet_audit.h が有効時だけパケット番号をビットマップで記録する。
  ペイロードの内容は保存しない。通常は１フレーム１行で、大きなフレームは
  logcat で切れない長さに分割する。通常受信時に毎パケットのログは出さない。
  受信側は最大128フレーム分を保持して、古いものから出力する。
  さらに遅い到着は追加フラグメントとして記録し、集計時に集合として統合する。
  終了時に残りを出力するので、強制終了・途中からのログ取得は使用しない。
  連番の欠落、壊れたJSON、endなしは集計エラーにして、低い欠落率を捏造しない。
  フレーム番号が飛んでも、送信側に実際の記録がないフレームはロスに数えない。
  送信成功は OS への引き渡しであり、電波での送信成功を保証しない。
  OS のキュー、無線再送、デコーダー以降の表示遅延は直接は測定しない。
  計測による負荷は実機で未評価。計測ON/OFFでの比較も行う。

  AddressSanitizer / UndefinedBehaviorSanitizer を有効にした計測器でも成功。
  送信処理、接続処理、セッション処理、受信処理の構文チェックが成功。
  既存のビルド設定には生成ヘッダー等の不足があったため、構文チェックは

  セッション処理の構文チェックでは Openhouse / libsurvive を無効にした。

既存コードで分かったこと
  common/wivrn_packets.h: video_stream_data_shard
    stream_item_idx / frame_idx / shard_idx でパケットを識別できる。
    view_info は先頭、timing_info は末尾にある。総 shard 数は明示されない。
    末尾を受信できた場合だけ、shard_idx + 1 から総数を確定できる。

  server/encoder/video_encoder.cpp: present_image / encode / SendData
    IDR 確認待ちなどで、送信前にフレームがスキップされる。
    frame_idx の飛びを、そのままネットワークで失われたフレームに数えない。
    SendData は UDP と TCP の両方を使う。送信経路を分けて集計する。
    送信例外はここで握りつぶされるため、送信試行と成功も分ける必要がある。

  client/decoder/shard_accumulator.cpp: insert / push_shard / try_submit_frame
    重複、古いフレームへの遅着、受信期限までの欠落を観測する入口になる。
    現在と次のフレームを保持し、後続フレームの進行で未完成フレームを見切る。
    末尾未受信の場合、既存ログの missing は欠落数の下限でしかない。
    frame_diff > 2 の経路では、途中の全フレームについて個別の情報は残らない。

  client/scenes/stream_gui.cpp / server/driver/wivrn_session.cpp
    既存の統計と Perfetto は帯域・フレームの時刻情報が中心。
    feedback に受信 shard 数や期待総数はなく、これだけで欠落率は出せない。

測定値の定義
  A. 再構成を見切った時点での未着
     表示に間に合わなかったパケット。FEC の効果を判断する主な対象。
  B. 見切った後の遅着
     A の一部。重複と区別し、有限の観測窓内で追跡する。
  C. 観測窓を過ぎても未着
     アプリでの未受信。無線区間だけが原因とは断定しない。
     OS の受信キューや送信側のドロップなども含み得る。
  D. 未完成フレーム、デコード出力なし、同じ映像の再表示
     別々に数える。いずれも直接のパケットロス率ではない。

初期設計方針（上記実装の元になった案）
  1. 明示的に有効化した場合だけ集計し、低頻度の構造化ログを出す。
     毎パケットの通常ログ出力は避ける。セッションとストリームで区別する。
  2. 受信側でユニーク受信数、重複、順序逆転、遅着を数える。
     再構成完了数と未完成数、末尾を受信したかも記録する。
     末尾を失ったケースは総数不明として残し、推測の率を出さない。
  3. 正確な照合のため、送信側にもフレームごとの総 shard 数、経路、
     送信成功・失敗を記録する。両端のログを frame_idx 等で突き合わせる。
     送信側成功は OS への引き渡しであり、電波での送信成功とは限らない。
     両端で同じ接続を識別できるようにし、再接続での番号再利用を混ぜない。
  4. まず既存プロトコルを変えずに測る。両端ログでは不便な場合に限り、
     総 shard 数や UDP 通し番号のプロトコル追加を別途検討する。

FEC の判断に必要な集計
  同一ストリーム・同一フレーム内の欠落数分布と、連続欠落の長さ。
  想定する 8 パケット等のグループごとの欠落数も評価する。
  1 秒等の区間別の欠落・遅着、受信間隔、送信量、再表示との相関。
  全区間平均だけでなく、短時間に集中したロスを確認する。
  フレームをまたぐ連続欠落は送信ログから順序を確認する。

検証条件
  欠落なし、単発欠落、連続欠落、先頭・末尾欠落、全フレーム未着、
  順序入れ替わり、重複、遅着、送信前スキップ、送信失敗、再接続を再現する。
  最後の未完成フレームも観測終了時点で記録し、未確定な値を区別する。
  TCP 映像と UDP 映像を混同しない。
  実機では同じ映像ビットレート等の条件で比較し、計測 ON/OFF の負荷も確認する。
  故意のロス注入は対象と実行方法を決めてから行う。今回の調査では未実施。
